What this demonstrates

An on-premise RAG architecture for privacy-sensitive legal workflows, where data residency, legal professional privilege, and operational control are important design constraints.

Tech stack: Python, FastAPI, PostgreSQL, Qdrant, sentence-transformers, llama.cpp/Ollama, NZLII ingestion pipeline, intent-aware legal ranker, heuristic court planner, conditional BM25, REST API, MCP server integration, domain-specific retrieval benchmark suite (30-query gold dataset, MRR / Hit@K metrics).

Architecture

Ingestion pipeline:
  NZLII / legislation sources
    -> HTML/PDF parsing + PDF fallback for pre-2000 scanned decisions
    -> metadata extraction (court, year, parties, citations)
    -> section-aware chunking (120-word windows)
    -> sentence-transformer embeddings (nomic-embed-text-v1.5)
    -> Qdrant vector index (deterministic UUID5 point IDs, idempotent)
    -> PostgreSQL relational store (documents, chunks, sentencing_cases,
       employment_cases - structured metadata for filtered search)

Query pipeline:
  User question
    -> heuristic court planner (no LLM): detects jurisdiction from domain
       signals - criminal/NZCA+NZHC, employment/NZERA, tenancy/NZTT, ACC,
       human rights/NZHRRT, statute sections/NZLEG. Extracts year from
       temporal phrases. Benchmarked: achieves oracle-equivalent quality.
    -> SQL pre-filter: PostgreSQL narrows candidates by court, year, offence,
       grievance type, or outcome fields (sentencing tracker / PG tracker)
    -> Qdrant semantic search within filtered candidate set
    -> intent-aware legal ranker: four profiles - authority (court hierarchy
       + citation density), example (recency boost), tracker (structured
       payload bonus), statute (legislation-first weighting). MRR +37% vs
       unranked baseline, zero coverage regressions.
    -> conditional BM25 (activated only for section refs, citations, quoted
       phrases, short keyword queries): OR-joined anchor extraction avoids
       AND-strictness. RRF-fused with vector results when active.
    -> context assembly + local LLM generation (llama.cpp/Ollama)
    -> citation verifier (regex, no extra LLM call)
    -> citation-backed answer with source URLs

How it works
The court planner detects "employment" and routes to NZERA + NZEmpC. PostgreSQL filters to those courts, Qdrant ranks by vector similarity, and the intent-aware legal ranker applies the authority profile (court hierarchy + citation density). The top passages are assembled and the LLM generates an answer - each claim linked to a source decision with court, date, and citation.

Structured trackers

Beyond free-text RAG, the system extracts structured fields at ingest time via regex and a local LLM, storing them in PostgreSQL and Qdrant payload. PostgreSQL pre-filtering narrows the candidate set before semantic search - comparable to Westlaw NZ tracker products but fully on-premise:

Sentencing Tracker
Starting point, final sentence, guilty plea discount, home detention, offence flags - across NZHC, NZCA, NZSC decisions.
Personal Grievance Tracker
Grievance type, reinstatement outcome, contributory conduct, compensation - across ERA and Employment Court decisions.

Known limitations

  • Full coverage currently focuses on NZCA 1985-2026; other courts have partial coverage.
  • Pre-2000 decisions sourced from scanned PDFs - OCR quality varies.
  • Answers depend on source availability and chunking quality; some complex multi-issue cases may be under-represented.
  • Research prototype only - not a replacement for professional legal advice.
